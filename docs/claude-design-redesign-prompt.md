# 프롬프트 본문 (여기부터 복사)

당신은 산업용 장비 제어/진단 소프트웨어 UI/UX 전문 디자이너입니다. 아래에 상세히 기술한 기존 웹 애플리케이션 **"FanCM"**의 UI/UX를 전면 재설계해 주세요. 기능은 하나도 빠뜨리지 말고 모두 수용하되, 정보 구조(IA)와 시각 디자인은 자유롭게 재구성해도 됩니다.

## 1. 제품 배경

- FanCM은 **RS-485 / Modbus RTU로 BLDC 팬모터(EC-FAN)를 제어·설정·진단하는 브라우저 앱**입니다. Chrome/Edge의 Web Serial API를 사용하며 서버 없이 동작하는 단일 페이지 vanilla JS 앱입니다.
- 처음에는 특정 고객사 하나(ebm-papst MODBUS 파라미터 스펙 호환 팬)를 타겟으로 시작했고, 개발 과정에서 필요한 기능들(펌웨어 업데이트, 생산라인 검사 도구, 오실로스코프급 차트 등)이 임시로 하나씩 덧붙여지며 유기적으로 커졌습니다. 그 결과 화면마다 스타일이 다르고(일부 Toss 스타일, 일부 기본 스타일, 인라인 스타일 대량 혼재), 기능 배치가 "추가된 순서"를 따르고 있어 탐색이 어렵습니다.
- 이제 **새로운 종류의 팬모터 제품군이 추가**되면서, 단일 고객사 전용 도구에서 **여러 팬모터 모델을 다루는 범용 제어/진단 플랫폼**으로 재탄생시키려 합니다.

## 2. 사용자층과 핵심 시나리오

| 사용자 | 주요 시나리오 |
|---|---|
| 사내 개발/펌웨어 엔지니어 (헤비 유저) | 파라미터 튜닝, 터미널로 프레임 직접 송신, 4채널 차트로 파형 분석, 펌웨어 업데이트 |
| 생산라인 작업자 | 하드웨어 검증(HW Overview 14항목), 전류/홀센서 오프셋 캘리브레이션, 시리얼 넘버 기록, OS 검증 53개 테스트 |
| 고객/필드 엔지니어 | 디바이스 스캔·연결, 대시보드 모니터링, 운전 조작(setpoint), 기본 설정, 알람 진단 |

## 3. 재설계 목표

1. **범용성**: 팬 모델/프로토콜 세대마다 지원 기능이 다릅니다. 연결된 디바이스가 지원하는 기능에 따라 UI가 적응하는 구조(미지원 기능은 숨김 또는 비활성+사유 표기)를 설계하세요. 현재는 "개발자 모드" 플래그 하나로 숨김/노출을 조절하는데, 이를 **디바이스 능력(capability) + 사용자 역할(role)** 2축으로 일반화하고 싶습니다.
2. **역할 기반 화면 분리**: 일반 사용자 화면(모니터링/조작/기본 설정)과 엔지니어 화면(터미널, 제조 도구, OS 검증, 서보 튜닝)을 명확히 분리. 제조(Manufacture) 기능이 숨김 탭으로 존재하는 현재 패턴을 더 체계적인 모드 전환으로 승격.
3. **정보 위계 재구성**: "연결 → 발견 → 모니터링 → 조작 → 설정 → 진단 → 유지보수(펌웨어/캘리브레이션)" 흐름이 자연스럽게 이어지도록 내비게이션을 재설계.
4. **일관된 디자인 시스템**: 색/타이포/간격/상태색 토큰 정의, 모든 화면에 일관 적용. 한국어/영어가 화면마다 혼재하는 현재 상태를 정리할 수 있게 라벨 체계도 일관되게(추후 i18n 가능한 구조).
5. **확장 대비**: §7의 예정 기능들이 들어올 자리를 미리 설계.

## 4. 현재 UX의 알려진 문제점 (실사용에서 확인된 페인포인트 — 반드시 개선안을 제시할 것)

1. **조작 화면과 차트 화면의 분리**: 파형(차트)을 보면서 setpoint를 조작하는 것이 튜닝/시험의 기본 워크플로우인데, 지금은 조작(Dashboard)과 관찰(Chart)이 별도 페이지라 매번 화면을 전환해야 합니다. 차트를 보면서 최소한 대상 디바이스의 setpoint·시작/정지·모드 전환이 가능한 구조(도킹 조작 패널, 스플릿 뷰, 오버레이 컨트롤 등)를 제안해 주세요.
2. **Serial Port 연결 패널의 상주 필요성**: 현재 사이드바 상단에 연결 설정(Baud/Parity 등)이 상주하고, 연결되면 접히기만 합니다. 연결 후에는 거의 건드릴 일이 없는 설정이 항상 자리를 차지하고 있는 셈입니다. 연결 플로우를 진입 시점의 온보딩(첫 화면 또는 모달)으로 옮기고, 평시에는 컴팩트한 연결 상태 인디케이터 + 재연결/설정 진입점만 남기는 방향을 검토해 주세요.
3. **다중 제품군의 식별**: 지금까지는 한 가지 제품만 다뤄서 문제가 없었지만, 여러 종류의 팬모터가 한 버스에 섞여 연결되면 어떤 디바이스가 어떤 제품인지 직관적으로 구분하기 어렵습니다. 두 시점을 모두 설계해 주세요 — ① **초기**: 연결/스캔 시 제품을 선택·식별하는 플로우, ② **운용 중**: 대시보드에서 제품군별로 분리해 보여주는 방법(그룹핑, 필터, 모델 배지, 색상 코딩 등).
4. **All Device Control의 이질감**: 특정 고객사 요청으로 급히 추가된 일괄 제어 섹션이라 대시보드 상단에 항상 펼쳐져 있고 UI 통일성을 해칩니다. 기능 자체(다중 선택 → 일괄 지령/정지)는 유지하되, 디바이스 선택 동작과 자연스럽게 통합된 형태(예: 디바이스를 선택하면 나타나는 컨텍스트 액션 바)로 재해석해 주세요.

## 5. 현재 구현된 기능 전체 인벤토리 (모두 수용할 것)

### 5.1 전역 레이아웃
- **상단 네비바**: ☰ 사이드바 토글, LS 로고, 앱 타이틀. 우측에 통신 통계 칩(REQ/OK/ERR/성공률/N프레임당 에러 — 호버 시 디바이스별 상세 툴팁 + 통계 리셋), 통신 모니터 토글 버튼.
- **좌측 사이드바**: ① Serial Port 연결 패널(Baud 9600~115200 / Parity / Data / Stop 선택, Connect 버튼, 연결상태 배너), ② 페이지 메뉴: Dashboard / Device / Chart / Terminal (+개발용 숨김 페이지 1개), ③ 하단 Settings 버튼.
- **Communication Monitor**: 우측 슬라이드 패널(리사이즈 가능). TX/RX 프레임 실시간 로그, HEX/DEC 토글, Auto Scroll, 패킷 카운트, Clear.
- 토스트 알림(진행률 토스트 포함), 확인 모달, 라이트 테마 단일(다크모드 없음).

### 5.2 Dashboard
- **All Device Control**: 디바이스 다중 선택(전체 선택/해제, 선택 칩), RPM/% 모드 토글, 프리셋 버튼(0/25/50/75/100%), setpoint 입력, 일괄 적용/정지.
- **Device List**: 카드형/목록형 뷰 전환, 전역 Live Watch(폴링) 토글, Auto Scan, Add Device(이름/Slave ID/기본 운전모드), 빈 상태 안내.
- **디바이스 카드** (정보 밀도가 매우 높음 — 재설계 중점 대상):
  - 헤더: 선택 체크박스, 이름(클릭 편집), 시리얼 넘버, ID 배지(클릭 시 Fan Address 편집), 삭제.
  - 액션: 디바이스별 Live Watch 토글, 알람 리셋, 소프트웨어 리셋, ⚙ 설정 모달.
  - 본문: 모터 상태 인디케이터(+툴팁), 알람코드 칩, RPM/% 모드 버튼, Setpoint·Actual 값 표시, setpoint 입력, Quick 프리셋 버튼(우클릭으로 값 커스텀).
  - **Monitoring Parameters**(접이식): 카드에 임의 파라미터를 추가해 실시간 감시 — 파라미터 목록 선택 또는 수동 입력(타입+주소+이름).

### 5.3 Device 페이지 (좌측 디바이스 목록 + 우측 서브탭 5개)
- **Configuration**: 카테고리 사이드바 + 설정 폼. 카테고리: 모터 제어(동작모드/지령소스/회전방향/최대속도/가감속), 센서 입력(지령소스/최소·최대값/커브 포인트), 보호 설정(최대 코일전류/온도 디레이팅), 통신 설정(Fan Address/Baud/Parity/종단저항), 시스템(리셋/EEPROM), 알람 설정(알람별 enable 토글 + Write All). 개발자 전용 카테고리: 모터 정보, 서보 튜닝(관성비/P게인/적분시상수/토크제한 등), 제품설정. 항목별 read/write 상태 표시와 개별 컨텍스트 메뉴.
- **Parameters**: 전체 레지스터 테이블(약 176행: holding 100 + input 29 + 제조사 전용 47). Read All, 행 단위 read/write, 타입 필터(All/Holding/Input/LSM), 구현여부 필터, 검색, CSV Import/Export/기본값 로드, 파라미터 수동 추가.
- **Information**: 시리얼 넘버 + 펌웨어 버전 4종(MCU Boot/FW, Inverter Boot/FW) 조회.
- **Update (펌웨어)**: 소스 선택(로컬 드래그앤드롭 .bin/.hex/.fw ↔ 온라인 버전 목록+다운로드), 프로토콜 설정(Auto/Fast/Legacy, 패킷 크기, 응답 대기), 4단계 진행 표시(초기화→Erase→데이터 전송(진행률/남은시간)→완료), 통신 로그, 검증/시작/취소.
- **Manufacture (숨김, 생산라인용)** — 서브탭 4개:
  - *HW Overview*: 하드웨어 검증 14항목 카드(485/USB 통신, OS 버전, 모터 ID, 시리얼, DC-link 센싱, IGBT 온도, 입력 결상, Hall 센서 등) + Total/Passed/Failed/Pending 통계, 항목 클릭 실행, Hall 미니차트.
  - *Offset Setting*: 전류 오프셋(Iu/Iv/Iw)·Hall 오프셋(U/V/W) 캘리브레이션, 상태/알람 표시, 실시간 차트 2종(Hall 3채널, Clarke α-β 극좌표 궤적 — 진폭/편심지수/전기각).
  - *OS Verification*: 53개 테스트 러너(5개 카테고리 아코디언: RS485/Modbus RTU/기본동작/구동동작/보호동작), Run All/Reset, 테스트별 목적·장비·진행률·단계·실행 로그·판정 기준·결과.
  - *Serial Number*: 패스워드 확인 → 시리얼 생성기(제품구분/연도/월/일련번호, 9자 규격) → 디바이스 기록, 그리고 읽기+디코드 표시.

### 5.4 Chart (오실로스코프급 — 복잡도 최상)
- 메인 캔버스: 휠 Y줌, 드래그 팬, 우클릭 마커, 커서 값 오버레이.
- 컨트롤 바: Start/Stop/Clear, Split View, Y축 모드 3종(Independent/Normalize/Scale+Offset), 커서 토글, 대상 ID, Pts/Samples/Range 통계, CSV/PNG export, 패널 접기.
- 하단 탭: **Channels**(CH1~4 — 색상/파라미터 피커/Auto·Min·Max/Scale·Offset/현재값 + Time Base: continuous/trigger 모드, 샘플링 0.125ms~1000ms) / **Trigger**(소스, 에지, Single/Normal, FFT 차트, Level/Position/샘플수, 트리거 이력, 비교 차트) / **Cursor Measurement** / **Freq. Response Function**(예정).
- 계측 CSV 포맷(.lsm, LMS SCADAS 호환) export 지원.

### 5.5 Terminal
- Modbus 프레임 수동 구성/전송: Slave ID, FC 01/02/03/04/05/06/15/16 + 제조사 확장(CANopen SDO 터널링 — Upload/Download, Object Index/Sub-Index), 주소/수량/값의 10진·16진 자동 변환 힌트.

### 5.6 Settings 모달
- Statistics(에러율 기준 프레임 수) / Auto Scan(ID 범위, 타임아웃, 스캔 레지스터, 미발견 디바이스 자동삭제) / Simulator(가상 슬레이브 — 하드웨어 없이 데모/개발) / Port Scan / Polling(간격/타임아웃/파라미터 간 딜레이).

### 5.7 프로토콜 다양성 (범용화의 근거)
한 앱이 이미 5계층의 프로토콜을 다룹니다. 디바이스 모델에 따라 지원 범위가 다릅니다:
1. 표준 Modbus RTU (FC03/04/06/16 등) — ebm-papst 호환 레지스터 맵
2. CANopen SDO 터널링(FC 0x2B) — 제조사 전용 파라미터·시리얼·펌웨어 버전
3. 펌웨어 업데이트 전용 프로토콜 2종(Legacy/Fast)
4. 고속 연속 스트리밍 + 트리거 캡처(차트용, 4채널)
5. 가상 슬레이브 시뮬레이터

## 6. 기술 제약 (디자인이 존중해야 함)

- 데스크톱 Chrome/Edge 전용(Web Serial API). **데스크톱 우선**, 모바일은 조회 수준이면 충분.
- RS-485 반이중 버스: 동시에 한 프레임만. 모든 쓰기/읽기는 폴링 사이클 사이에 큐로 직렬화 → 조작 후 반영까지 수십~수백 ms 지연. **"전송 대기 → 쓰는 중 → 확인됨/실패" 상태 피드백**이 UX적으로 매우 중요합니다.
- 한 버스에 다수 디바이스가 물리며 디바이스 수가 늘면 갱신 주기가 느려짐 — 갱신 신선도(마지막 갱신 시각/주기)를 정직하게 표시할 방법 필요.
- 값 변환이 모드 의존적(RPM↔raw, %↔raw). 단위 표기가 항상 명확해야 함.
- 산출물은 정적 HTML/CSS(+최소 JS) 목업으로, 기존 vanilla JS 앱에 점진 적용 가능해야 합니다. 특정 프레임워크(React 등) 의존 금지.

## 7. 예정 기능 (자리를 미리 설계할 것 — 스펙 기반 로드맵)

- **I/O 핀 구성**: IO1~3 용도 설정 — 2단 선택 UI(물리 모드 선택 → 그 모드가 서비스할 논리 기능 연결)
- **Fail-safe**: 신호 상실 시 안전 속도/방향 자동 전환(지연시간/안전값 설정)
- **Parameter Set 1/2**: 설정 세트 2개 + 전환 소스 + 세트별 P/I 게인 튜닝 UI
- **Enable/Disable**: setpoint와 독립된 구동 차단(정비 잠금 성격)
- **Power Limiter**: 온도 디레이팅 곡선 + 활성화 스위치 + 램프
- **Error History**: 디바이스 내장 최근 13건 에러 + 발생 시각(누적 운전시간 기준) — 원격 진단 뷰
- **텔레메트리 확장**: 모터 온도, 전력(W), 누적 전력량(에너지 관리), 운전시간 카운터
- **제한 상태 알림**: 과변조/전류/파워 제한이 걸렸을 때 상시 배지 + 원인 설명
- **시리얼번호 기반 자동 어드레싱**: 다수 팬 동시 설치 커미셔닝 마법사
- **Password 권한 3단계**(제조사/고객사/최종사용자): 파라미터별 쓰기 권한 — 역할 기반 UI 노출과 자연스럽게 통합되어야 함
- 기타: Shedding(동결 방지 기동), 0-10V 출력 곡선, 센서 단위 문자열, Factory/Customer 설정 백업·복원, 경고/에러 릴레이 마스크·지연, 로터 센서 캘리브레이션, RFID, 고객 스크래치 데이터 16칸

## 8. 산출물 요구사항

1. **정보 구조(IA) 제안**: 전체 내비게이션 트리 + 각 화면의 역할 정의. 현재 5페이지 구조를 유지할 필요 없음.
2. **디자인 토큰**: 색(브랜드/상태/차트 채널), 타이포 스케일, 간격, 라운딩, 그림자. 라이트/다크 모두.
3. **핵심 화면 HTML 목업** (우선순위 순):
   - ① 대시보드(디바이스 카드 + 일괄 제어 + 연결/스캔 흐름)
   - ② 디바이스 상세(Configuration/Parameters/Information/Update 통합)
   - ③ 차트(오실로스코프)
   - ④ 제조 모드(HW 검증/오프셋/OS 검증/시리얼)
   - ⑤ 터미널 + 통신 모니터 + Settings
4. **상태 표현 규약**: 연결/해제, 온라인/오프라인, 폴링 중, 쓰기 대기→진행→확인/실패, 알람/경고, 제한 걸림 — 색+아이콘+텍스트 삼중 표현(색맹 대응).
5. **역할/능력 게이팅 규약**: 사용자 역할(일반/엔지니어/제조) × 디바이스 능력에 따른 노출 규칙을 컴포넌트 수준에서 어떻게 표현할지.
